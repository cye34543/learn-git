# 第13章：思维图 (Graph of Thought / GoT)

> 不剪枝，而是把多个思路交织在一起，让它们互相影响、互相增强。

---

## ToT 的问题 vs GoT 的解法

Tree of Thought 问：**哪个分支赢了？**

Graph of Thought 问：**多个分支怎么互相作用，产生更好的答案？**

```
ToT:                              GoT:
分支1 分支2 分支3 分支4           分支1  分支2  分支3  分支4
  |     |     |     |              |   \  /  \    /
 评分  评分  评分  评分            |  对比  |  对比
  |     |     |     |              |     \ |  /
 剪掉  保留  剪掉  剪掉            |    精炼  精炼
        |                          |    /  \  /
       答案                        |  综合  综合
                                   \    |   /
                                    \   |  /
                                     答案（融合了所有视角！）
```

---

## GoT 的图操作

| 操作 | 在这个例子中做了什么 |
|------|---------------------|
| **分支** | 产生4条竞争假设 |
| **评分** | 排名，但全部保留在图里 |
| **对比** | 把不同意见变成新的诊断信号 |
| **精炼** | 用强的分支改进弱的分支 |
| **聚合** | 把多个来源融合成综合视图 |
| **结论** | 使用所有线的洞察得出最终答案 |

---

## 为什么 GoT 产出的答案更完整？

ToT 挑一个赢家，其他丢掉 → 答案可能片面

GoT 保留所有分支，通过对比、精炼、聚合让它们互相增强 → 答案包含矛盾、包含被拯救的弱信号、结构更完整

**教程中展示的核心操作：**
- 倦怠型(9分) 对比 回避型(6分) → 产生新的诊断信号
- 外部压力型(4分) 被倦怠型精炼后 → 弱假设被拯救并改进
- 多个综合节点融合 → 最终结论整合了所有线索

---

## 什么时候用 GoT？

✅ **适合的场景：**

**运维场景**：区域性故障，症状互相矛盾
- 分支：网络路由、数据库复制延迟、认证服务超时
- 对比：配对矛盾的分支（"网络正常" vs "超时是网络形状的"）
- 精炼：用新数据更新弱解释
- 聚合：构建综合故障模型
- 结论：协调多因素的修复方案

**开发场景**：不稳定的 E2E 测试
- 分支：竞态条件、时钟偏移、测试数据耦合、外部API不确定性
- 对比：用失败追踪和时间戳对比假设
- 精炼：用日志证据改进弱假设
- 聚合：构建综合解释

**Agent 构建场景**：研究级规划 Agent
- 分支：不同的任务分解和工具序列
- 对比：让计划互相批评，暴露隐藏假设
- 精炼：用强计划改善弱计划
- 聚合：合并互补子计划

---

## ToT vs GoT 决策指南

| 用 ToT | 用 GoT |
|--------|--------|
| 需要快速、单一的可执行方向 | 问题模糊，多条线索都需要考虑 |
| 时间紧迫 | 弱信号可能经过精炼变得有价值 |
| 保持多分支成本高于丢失信息风险 | 需要最终答案包含矛盾而非隐藏矛盾 |

---

## 一句话总结

GoT 不剪枝，而是用图的结构让多个思维分支互相作用。对比产生洞察、精炼拯救弱假设、聚合产生高质量综合。用得好的话，答案不是"更好看"，而是"结构上更完整"。

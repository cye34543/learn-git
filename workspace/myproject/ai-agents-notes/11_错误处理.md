# 第11章：错误处理与弹性设计

> Agent 比普通程序更容易出错，因为它的每一步都依赖不可靠的组件。这章教你系统性地应对失败。

---

## 为什么 Agent 的错误处理更复杂？

Agent 串联了三个不可靠的环节：

1. **LLM 调用** — 可能超时、返回乱码、消耗完资源
2. **工具执行** — 可能网络挂了、参数不对、服务不可用
3. **工作流逻辑** — 可能策略阻止、部分完成、依赖断裂

---

## 三大核心思路

### 1. 标准化的错误分类

用一套固定的错误码，而不是每次 instanceof 判断：

| 错误类 | 代码 | 可重试？ |
|--------|------|----------|
| `ValidationError` | VALIDATION_ERROR | 通常不 |
| `LLMCallError` | LLM_CALL_FAILED | 通常可以 |
| `ToolExecutionError` | TOOL_EXECUTION_FAILED | 部分可以 |
| `AgentWorkflowError` | AGENT_WORKFLOW_FAILED | 看情况 |

每个错误都包含：
- `code`：机器可读的错误码
- `userMessage`：给用户看的安全信息
- `retryable`：是否应该自动重试
- `details`：给开发者的详细信息
- `cause`：原始错误（保留根因链）

### 2. 分类 + 恢复策略

```
失败 → 标准化错误 → 分类判断 → 
├─ 可重试 → 指数退避 + 抖动 → 重试
├─ 有备用方案 → 降级到备选方案
├─ LLM整个挂了 → 确定性降级模式
└─ 无法恢复 → 返回用户友好错误 + 关联ID
```

### 3. 用户和开发者看到不同的信息

**用户看到：**
- 清晰的下一步建议
- 一个参考编号（方便联系客服）
- 没有技术细节

**开发者看到：**
- 错误码
- 结构化细节
- 关联ID
- 原始错误链

## 关键策略详解

### 超时
```javascript
// Promise.race：工作和计时器比赛
function withTimeout(promise, ms, label) {
    return Promise.race([
        promise,
        new Promise((_, reject) => 
            setTimeout(() => reject(new AppError('TIMEOUT')), ms)
        )
    ]);
}
```

### 重试（带退避和抖动）
```
第1次失败 → 等1秒 → 重试
第2次失败 → 等2秒 → 重试  
第3次失败 → 等4秒 → 放弃
(+ 随机抖动避免多个客户端同时重试)
```

### 降级模式
```
正常路径: LLM → 工具1 → 工具2 → 回答
                   ↓ (工具1挂了)
降级路径: 跳过LLM → 工具1(重试) → 失败
                → 备用工具 → 回答(标注降级)
```

---

## 经验法则

1. 每个 LLM调用和工具调用都要设超时
2. 只重试临时性错误（不要重试验证错误）
3. 重试要加抖动（避免雪崩）
4. 每条用户可见的错误都要带关联ID
5. 用户和运维看到的东西要分开

---

## 一句话总结

Agent 一定会出错 — LLM 会超时、工具会挂、工作流会断。正确的做法不是祈祷不出错，而是把每种失败都分类、用统一的策略处理、给用户清晰的降级体验。这套错误处理机制是生产级 Agent 的底线。

# 第6章：流式输出与响应控制

> 不想等10秒才看到回复？用流式输出，一个字一个字地看 AI "打字"。

---

## 普通模式 vs 流式模式

```
普通模式（非流式）:
用户: "解释一下闭包"
[等10秒...什么都没发生...]
回复: "闭包是 JavaScript 中一个函数..." (一次性全出来)

流式模式:
用户: "解释一下闭包"
"闭包"(0.1秒→立刻看到第一个字！)
"是"(0.2秒)
"JavaScript"(0.3秒)
...
[持续打字效果，看起来更快]
```

---

## 流式输出怎么实现的？

LLM 内部是一个令牌一个令牌生成的，流式模式只是把这些令牌**逐个**发给你，而不是攒齐了再发：

```
内部生成:
令牌1: "闭包"
令牌2: "是"
令牌3: "JavaScript"
令牌4: "中"
...

不流式: 等全部生成完 → 一次性返回
流式:   onTextChunk("闭包") → onTextChunk("是") → ...
```

---

## 回调函数 onTextChunk

```javascript
const answer = await session.prompt(query, {
    maxTokens: 2000,           // 限制回复最多2000令牌
    onTextChunk: (text) => {   // 每生成一个文本块就触发
        process.stdout.write(text);  // 实时打印
    }
});
```

---

## 令牌限制 (maxTokens)

不设上限的话，LLM 可能没完没了地生成：

```
没限制: "闭包是JavaScript中...（说了1万字还在说）"
有限制: "闭包是JavaScript中...（到2000令牌就停）"
```

**经验值：**
- 简短回答: 50-100 令牌
- 详细解释: 2000 令牌（本章例子）
- 长文章: 3000+ 令牌
- 不设限: 危险，可能耗尽整个上下文窗口

---

## 流式输出的应用场景

| 场景 | 为什么用流式 |
|------|------------|
| 聊天界面 | 用户看到"对方正在输入"的效果 |
| 网页应用 | 通过 WebSocket 推送给浏览器 |
| CLI 工具 | 终端逐字显示 |
| 多消费者 | 同时写入控制台、文件、网络 |

## 性能参考

```
模型大小     GPU(RTX 4090)     CPU 纯推理
1.7B参数     50-80 令牌/秒     15-25 令牌/秒
8B 参数     20-35 令牌/秒     5-10 令牌/秒
20B参数     10-15 令牌/秒     2-4 令牌/秒

用户体验:
首令牌时间 < 500ms → 感觉即时
令牌速度 > 20/秒 → 阅读自然
```

---

## 一句话总结

流式输出让用户立刻看到模型在工作，体验好多了。加上 `maxTokens` 控制回复长度，避免模型滔滔不绝。这是所有用户界面 Agent 的标配。
